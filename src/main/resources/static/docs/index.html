    환경 설정

    의존성과 DB 설정#

    2.1 Gradle 의존성#

    기존 루트 build.gradle의 dependencies에 다음 의존성을 추가합니다.

    Groovy 서버 예시 · 미구현 
    implementation 'org.springframework.boot:spring-boot-starter-thymeleaf'
implementation 'org.springframework.boot:spring-boot-starter-validation'
    • Thymeleaf는 HTML의 th:* 속성을 처리하는 데 필요합니다.
    • Validation은 요청 DTO의 @NotBlank, @NotNull, @Size, @Min 등을 사용할 때 필요합니다.
    • Web MVC·Security·MyBatis·MySQL 드라이버는 이미 선언돼 있으므로 중복 추가하지 않습니다.
    • Spring Boot가 관리하는 라이브러리 버전은 임의로 개별 지정하지 않습니다. Boot 4에 맞는 의존성을 사용합니다.
    • 기존 Spring Boot 버전의 실제 다운로드 가능 여부와 저장소 접근은 Gradle로 확인해야 합니다. 이 가이드는 버전을 변경하지 않습니다.
    !

    이번 작업의 범위 밖 루트 빌드 파일 수정은 이후 백엔드 연결 작업에 해당합니다. 문서를 추가하는 작업에서는 build.gradle을 변경하지 않습니다.

    2.2 로컬 설정 예시#

    src/main/resources/application-local.properties 같은 로컬 프로필 파일에 설정합니다.

    Properties 서버 예시 · 미구현 
    spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}

mybatis.configuration.map-underscore-to-camel-case=true
mybatis.mapper-locations=classpath:/mappers/**/*.xml

# 개발 중 HTML 수정 내용을 바로 확인하기 위한 설정
spring.thymeleaf.cache=false

    DB_URL에는 jdbc:mysql://localhost:3306/spoit처럼 실제로 사용할 JDBC URL을 넣습니다. DB 이름·계정·권한·접속 옵션은 개발 환경에 맞춰 설정합니다. 비밀번호는 Git에 커밋하지 않습니다.

    • mybatis.mapper-locations는 XML Mapper를 사용할 때의 예시 경로입니다. 해당 XML을 실제로 작성해야 합니다. 애너테이션 Mapper만 사용한다면 생략할 수 있습니다.
    • Mapper 인터페이스에 @Mapper를 붙이거나 설정 클래스에 @MapperScan을 적용합니다.
    • 스키마 파일은 src/main/resources/schema.sql이 아니라 루트의 db/schema.sql입니다. 서버 실행만으로 자동 적용된다고 가정하지 않습니다.
    • 종목·지역 등 기준 데이터도 준비해야 합니다. DDL만 적용하면 목록 선택지에 필요한 데이터가 생기는 것은 아닙니다.
    !

    기존 데이터가 있는 DB에 그대로 실행하지 마세요 db/schema.sql에는 DROP TABLE IF EXISTS가 있습니다. 비어 있는 개발용 DB에 검토 후 적용하거나, 운영용 마이그레이션을 별도로 작성합니다.

    i

    문서에는 실제 접속 정보를 남기지 않습니다 예시의 환경변수 이름만 유지하고, 실제 DB 사용자명·비밀번호·운영 URL·세션 키는 문서와 저장소에 기록하지 않습니다.

    연결할 때의 주의사항#

    • HTML 화면은 @RestController가 아니라 @Controller에서 반환합니다.

    템플릿이 읽을 속성과 표시값 제공

    DB 행에는 matchId, startAt, feePerPerson 등이 있지만 화면은 dateLabel, feeText, statusLabel, canApply도 읽습니다. 컬럼명만 맞춰도 화면이 완성되는 것은 아닙니다.

    • DTO는 record 또는 getter가 있는 Java 클래스로 만들 수 있습니다.
    • 숫자 ID는 실제 엔티티·저장 DTO에서 Long, 금액은 BigDecimal, 날짜·시각은 용도에 맞게 LocalDate, LocalTime, LocalDateTime 등을 사용합니다.
    • 표시값은 서버에서 일관되게 포맷합니다. 예를 들어 feeText는 화면에서 원을 붙이므로 12,000 형태로 제공합니다.
    • 빈 컬렉션은 List.of()처럼 빈 목록으로 제공합니다. 화면이 접근하는 중첩 객체의 필수 속성도 채웁니다.
    • 익명 사용자의 currentMember는 null, unreadCount는 0으로 제공합니다. 실제 회원 객체 대신 임시 로그인 데이터를 넣지 않습니다.

    4.3 컨트롤러 연결 형태#

    다음은 서비스를 구현한 뒤 사용할 구조 예시입니다. MatchPageService는 현재 저장소에 없으며 직접 작성해야 합니다. listModel(...)은 위 표의 화면 모델 전체를 반환하는 메서드로 가정합니다. 반환값에는 검증되지 않은 요청값이나 비밀번호를 넣지 않습니다.

    Java 서버 예시 · 미구현 
    package co.kr.spoit.match;

import java.util.List;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;

@Controller
public class MatchController {
    private final MatchPageService matchPageService;

    public MatchController(MatchPageService matchPageService) {
        this.matchPageService = matchPageService;
    }

    @GetMapping({"/matches", "/matches/cards"})
    public String list(
            @RequestParam(name = "sportId", defaultValue = "all") String sportId,
            @RequestParam(name = "regionId", defaultValue = "all") String regionId,
            @RequestParam(name = "date", required = false) String date,
            @RequestParam(name = "hours", required = false) List<String> hours,
            jakarta.servlet.http.HttpServletRequest request,
            Model model) {
        model.addAllAttributes(matchPageService.listModel(
                sportId, regionId, date, hours == null ? List.of() : hours));
        return request.getServletPath().equals("/matches/cards")
                ? "matches/cards" : "matches/list";
    }
}

    이 예시는 목록 표시의 골격입니다. 공통 로그인 정보는 @ControllerAdvice의 @ModelAttribute 등으로 인증 정보에서 제공하고, 화면 서비스가 잘못 덮어쓰지 않도록 합니다.

    구현 시 주의사항#

    • 검색에는 all·빈 문자열이 들어오므로 검색 입구에서는 문자열로 받고 검증 후 수치로 변환합니다.
    • sportId·regionId 타입은 선택지 DTO와 search에서 맞춥니다. 문자열 "1"과 수치 1L 비교에 의존하지 않습니다.
    • hours는 반복 파라미터입니다. 단일 문자열로 받거나 첫 항목만 검색하지 않습니다.

    • 관리자는 한 템플릿에 여러 패널이 있습니다. hidden은 서버 평가를 멈추지 않으므로 비표시 패널이 참조하는 모델도 준비합니다.

    요청 흐름

    POST 폼과 참가 신청 흐름#

    6.1 요청 수신 방식#

    기존 폼은 일반 HTML 폼입니다. JSON 전송이 아니므로 보통 @ModelAttribute 또는 @RequestParam으로 받습니다. @RequestBody를 전제로 구현하지 않습니다.

    팀 참가 선택에는 다음 형태의 DTO를 준비합니다.

    Java 서버 예시 · 미구현 
    // DTO 구조 예시. 각 필드의 getter/setter를 구현해야 합니다.
public class MatchSelectionForm {
    private String applicationType;       // individual | team
    private Long clubId;                  // 개인 참가에서는 전송되지 않음
    private List<Long> clubMemberIds = new ArrayList<>();
}

    위 코드에는 java.util.List·java.util.ArrayList import가 필요합니다. private 필드만 선언하면 일반 프로퍼티 바인딩이 되지 않습니다. getter/setter 또는 적절한 생성자 바인딩을 구현합니다.

    • applicationType은 허용값을 검증합니다. team이면 clubId와 대상 팀원을 검증합니다.
    • 개인 참가에서는 팀 관련 입력이 disabled여서 전송되지 않습니다. 필드 누락을 정상적으로 처리합니다.
    • 체크하지 않은 체크박스도 파라미터가 아예 없을 수 있습니다. 복수 입력은 빈 목록, 동의값은 미동의로 처리합니다.
    • clubMemberIds는 회원 ID가 아니라 club_member.club_member_id 목록입니다.
    • 신청자의 userId·연락처·권한·요금·잔여 좌석은 전송값을 믿지 않고 인증 정보와 DB에서 읽습니다.

    6.2 매치 참가 신청#

    GET /matches/{matchId}

    2. match 모델과 currentMember를 설정하고 matches/detail 반환

    2. 본인·소속·중복·잔여 좌석 검증
    3. 선택 내용을 서버 세션에 저장
    4. /matches/{matchId}/apply로 리다이렉트
    GET /matches/{matchId}/apply
    1. 세션 선택과 최신 DB 상태로 selection / match / canReserve 구성
    2. matches/join 반환
    POST /matches/{matchId}/apply

    2. 트랜잭션 안에서 신청·참가자 등록

    세션 선택은 본인·매치에 연결하고, 다른 매치에 재사용하거나 오래된 선택을 다시 보내지 못하게 합니다. 재전송·동시 신청에서도 중복 등록이나 정원 초과가 발생하지 않도록 DB 제약과 적절한 잠금 등을 조합합니다.

    !

    신청 완료는 결제 완료가 아닙니다 현재 폼은 참가비·취소 안내 확인이며 실제 결제 서비스는 별도 설계가 필요합니다. 표시용 결제 수단 라디오값을 결제 요청으로 처리하지 않습니다.

    POST 후에는 원칙적으로 PRG(POST → Redirect → GET)를 적용합니다. 성공 문구는 저장 성공 후에만 표시하고, 업무 오류는 입력값과 화면 계약에 맞는 error 등을 반환합니다. @Valid를 쓰면 BindingResult를 대상 폼 인자 바로 뒤에 두고, 오류 시에도 선택지·공통 모델을 다시 설정합니다.

    7.2 기존 로그인 폼과의 대응#

    기존 로그인 폼 필드와 Spring Security 설정·서버 처리의 대응
    폼Security 설정·서버 처리
    POST /loginloginProcessingUrl("/login"). 보통 Security 필터가 처리
    emailusernameParameter("email"). 기본값인 username이 아님
    passwordpasswordParameter("password")
    remember기능 구현 시 rememberMeParameter("remember")
    redirect인증 성공 핸들러에서 내부 이동 경로 검증

    Security DSL의 해당 부분은 다음 형태입니다. 완성된 SecurityConfig가 아닙니다. 공개 범위·사용자 조회·실패/성공 핸들러 등을 별도로 구성합니다.

    Java Security 예시 · 미완성 
    http.formLogin(form -> form
        .loginPage("/login")
        .loginProcessingUrl("/login")
        .usernameParameter("email")
        .passwordParameter("password")
        .failureUrl("/login?error")
        .permitAll());
    • GET /login 컨트롤러에서 auth/login을 반환합니다. ?error가 있으면 사용자용 문구를 error 모델에 설정합니다. 원본 예외나 SQL 오류를 노출하지 않습니다.
    • UserDetailsService는 이메일로 app_user를 조회하고 저장된 password_hash와 역할을 Security에 전달합니다. 비밀번호는 적절한 PasswordEncoder로 검증합니다.
    • 인증 성공 후 검증된 redirect, 저장된 요청, 기본 페이지 등 이동 우선순위를 정합니다. 외부 URL·// 시작·역슬래시·제어문자 등을 거부하고 허용한 앱 내부 경로로만 이동합니다. hidden 값을 무조건 sendRedirect하지 않습니다.
    • 매치 상세의 로그인 링크는 해당 상세 화면으로 돌아갈 경로를 전달합니다. 성공 핸들러를 구현하지 않으면 이 명시적 복귀값이 자동 적용되지 않습니다.
    • 로그인 상태 유지는 체크박스만으로 작동하지 않습니다. remember-me 서비스·비밀키 관리·Cookie 속성·만료 및 로그아웃 처리를 구현합니다.
    • 폼의 member/facility/system과 Security의 GrantedAuthority는 별개입니다. 예를 들어 hasRole("SYSTEM")이면 인증 측에서 ROLE_SYSTEM을 부여합니다. 신청값 role=system만으로 관리 권한을 주지 않습니다.

    7.3 CSRF와 공통 회원 모델#

    기존 POST 폼에는 다음 hidden 입력이 있습니다.

    HTML Thymeleaf 예시 
    <input type="hidden" th:if="${_csrf != null}"
       th:name="${_csrf.parameterName}" th:value="${_csrf.token}" />
    • CSRF는 원칙적으로 유지합니다. 403을 피하려고 일괄 비활성화하지 않습니다.
    • _csrf는 Security가 제공합니다. 고정 토큰을 임의 생성하지 않습니다.
    • currentMember는 인증 사용자에서 만들고 userId·nickname·phone·initial 등 필요한 표시 정보만 담습니다. 비밀번호 해시는 포함하지 않습니다.
    • 마이페이지·관리자·팀장 권한은 서버에서 매번 검증합니다. 버튼 숨김이나 JavaScript 검사만으로는 보호되지 않습니다.

    기능 계약

    기능별 계약과 SQL 연결#

    아래 8개 장은 기능별로 현재 화면의 요청·입력값, db/schema.sql의 저장 구조·제약, 서버 처리 순서와 미정 정책을 설명합니다. 백엔드 컨트롤러·서비스·매퍼는 아직 구현되지 않았으므로 경로가 있다고 동작하는 API로 읽지 않습니다.

    화면 계약

    현재 템플릿·JavaScript에 있는 URL, 폼 필드, 모델, 표시값입니다. 실제 컨트롤러 구현을 뜻하지 않습니다.

    SQL 사실

    db/schema.sql에 선언된 컬럼·PK/FK·UNIQUE·CHECK입니다. 주석에만 있는 상태값은 DB 강제와 다릅니다.

    구현 권고

    트랜잭션·잠금·멱등성·오류 처리의 검토안입니다. 이미 구현된 동작이 아닙니다.

    결정 필요

    화면과 SQL 사이에 저장 위치나 정책이 정해지지 않은 항목입니다. 없는 테이블·API를 있다고 가정하지 않습니다.

    • 빈 값과 NULL: 폼의 빈 문자열은 SQL NULL과 다릅니다. 미배정 matchSide, 미선택 regionId, 반려 사유 등은 경로별로 NULL 허용 여부를 확인하고 명시적으로 정규화합니다.
    • CHECK의 한계: MySQL CHECK는 식이 UNKNOWN이면 통과할 수 있습니다. nullable 컬럼이 섞인 복합 CHECK를 업무 검증 전체로 해석하지 않습니다.
    • 삭제의 세 가지 방식: FK 기본은 RESTRICT입니다. deleted_at 논리 삭제, club_member.left_at 소속 이력, 알림 삭제 정책은 서로 다른 문제입니다.
    • 권한과 CSRF: URL 역할 검사만으로 충분하지 않습니다. 본인 소유, 팀장 여부, 담당 시설, 대상 리소스 상태를 함께 확인합니다. CSRF 토큰은 이 검사를 대체하지 않습니다.
    • 표시값과 저장값: 내부 MMR·0~10 평가·0~5 표시 레이팅, 한글 상태와 영문 CHECK 값을 같은 것으로 취급하지 않습니다.

    3. date+hours 또는 date+start/end를 실제 일시 구간으로 변환합니다. 시간대·종료 경계·비연속 블록을 명확히 정하고 운영 시간·휴관 예외와 겹치는지 검사합니다.
    4. 새 매치를 만들기 전에 최신 운영 가능 구간과 겹치는 매치 수를 확인합니다. 동시 생성에도 concurrent_match_limit를 넘지 않게 시설 단위 잠금 등 동일한 직렬화 기준을 검토합니다. 단순 SELECT COUNT 후 INSERT만으로는 동시성을 보장하지 않습니다.
    5. A/B 정원 합계를 max_participants로 구성합니다. min_participants, required_skill, created_by 등 필수값을 서버에서 정한 뒤 저장합니다. 프런트 feePerPerson은 BigDecimal로 검증하고 원화 표시와 구분합니다.

    화면 계약SQL 사실결정 필요

    운영 기능의 요청과 필드

    • match_side는 SQL에서 NULL 또는 A/B CHECK입니다. 미배정 빈 문자열은 NULL로 정규화해야 합니다. 선택 변경만으로 저장되지 않고 저장 버튼의 POST가 있어야 합니다.

    • social_match.assignment_method는 MANUAL/AUTO CHECK이며 기본값 MANUAL입니다. 정원 도달 시 자동 배정·완료 후 잠금은 현재 화면 정책이고 DB가 자동 수행하는 기능이 아닙니다. 자동 배정 알고리즘과 확정 메타데이터 기준은 서비스가 정합니다.
    • captain_a_participant_id/captain_b_participant_id의 복합 FK는 같은 경기 참가자임을 검증하고 두 값의 동일 여부를 제한합니다. 실제 A/B 소속·활성 상태·팀장 권한은 서버 검증입니다.
    • 이용 완료 폼은 서버의 match.status가 matched일 때 표시되고, 버튼은 서버가 제공한 match.bothTeamsAssigned가 참일 때 활성화됩니다. 템플릿이 양 팀 명단을 직접 세지는 않습니다. 화면 안내는 양 팀에 한 명 이상 배정되어야 한다고 설명하지만, 해당 모델 값의 산출과 전체 확정 참가자 배정·팀 정원 등 완료 요건은 서버에서 검증해야 합니다.
    • 이용 완료는 승무패 확정이나 레이팅 반영과 다릅니다. result_status/final_result/rating_status를 자동으로 갱신한다고 가정하지 않습니다.
    • 반려 reason의 전용 저장 컬럼은 match_application에 없습니다. UI에서 사유를 받으므로 기록 위치·보존·노출 정책을 정해야 합니다.

    처리 순서와 경합 구현 권고

    1. 확정·반려 전에 신청과 경기의 최신 상태, 시설 담당 권한, 이미 처리된 신청인지 확인합니다.
    2. 팀 배정 전에 참가자가 해당 경기의 활성 참가자인지, 대상 팀 정원이 남았는지 확인하고 빈 문자열은 NULL로 정규화합니다.
    3. 여러 참가자의 팀 이동은 하나의 트랜잭션과 일관된 잠금 순서로 처리해 동시 이동의 정원 초과를 막습니다.
    4. 이용 완료 시 양 팀 배정과 확정 참가자 전체 배정, 팀 정원을 검증하고 bothTeamsAssigned를 일관되게 구성합니다. 완료 후 팀 구성을 잠그는 현재 화면 정책도 서버에서 강제합니다.
    5. 확정·반려·완료에서 감사 로그와 알림을 실제로 기록할지, 생성 시점과 업무 저장 실패 시 함께 롤백할지 분리할지 결정합니다.

    • delivered_at은 전달 시각을 저장할 뿐 이메일·WebSocket 발송·재시도·전달 보장을 구현하지 않습니다. 같은 업무 이벤트의 중복 알림 방지를 위한 고유 이벤트 키도 없습니다.
    • 업무 저장과 DB 알림 삽입을 함께 처리할지, 외부 전달 실패는 outbox 등으로 분리할지 결정합니다. outbox는 현재 SQL에 없는 설계 제안입니다.
    • audit_log(528~539): audit_log_id, nullable actor_user_id, action, target_type, 문자열 target_id, detail, created_at. 대상 레코드 FK가 아니며 append-only나 변경 불가도 DB가 강제하지 않습니다.
    • 감사 detail에 비밀번호·초대 코드·세션 토큰 등을 남기지 않습니다. 감사 로그 보존·변경 권한·삭제 정책을 정합니다. 화면의 log.requestId 같은 추적 표시는 SQL audit_log_id와 다릅니다.

    설계 검토 구현 권고

    1. 업무 이벤트와 알림 생성의 트랜잭션 경계를 정합니다. 업무 저장이 롤백되면 알림·감사가 남지 않도록 할지, 별도 outbox로 재처리할지 결정합니다.
    2. 개인 알림과 관리자 알림 모두 수신자 본인 또는 허용된 관리자 역할을 매 요청에서 확인합니다.
    3. 읽음·삭제는 대상 ID만으로 처리하지 않고 recipient_user_id 조건을 함께 사용합니다.
    4. 감사 로그는 현재 자동 기록되지 않습니다. 실제 기록 서비스를 구현하고, 주요 변경과의 트랜잭션 경계·개인정보·비밀값 비노출·삭제·보존 정책을 정합니다.

    결정 필요와 검증 결정 필요
