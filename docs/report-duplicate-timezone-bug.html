신고 중복 조회 테스트 시간대 오류 보고서

작성일: 2026-11-10

현상

PR #106의 CI에서 전체 1,198개 테스트 중 신고 중복 조회 테스트 3개가 실패했다. 모두 최근 2~3초 이내에 저장한 신고를 10초 중복 조회 범위에서 찾지 못한 사례다.

  • duplicateLookupUsesDbClockWindow: 최근 신고 조회 실패
  • duplicateLookupComparesSummaryExactly: 동일 원문 조회 실패
  • duplicateLookupRespectsOtherKeys: 동일 신고 조건 조회 실패

CI 로그에는 실패한 단언의 실제 값이 남지 않았다.

원인

기존 테스트 헬퍼는 DB의 CURRENT_TIMESTAMP를 java.sql.Timestamp로 읽어 JVM 기본 시간대에 영향을 받는 LocalDateTime으로 변환한 뒤 테스트 데이터를 저장했다. 중복 조회는 DB의 CURRENT_TIMESTAMP를 기준으로 수행한다. JDBC 연결 시간대와 JVM 기본 시간대가 다르면 생성 시각과 조회 기준이 어긋날 수 있다.

이 문제는 테스트 데이터 생성 경로에서 확인됐다. 운영 신고 저장과 중복 조회는 모두 DB의 CURRENT_TIMESTAMP를 사용한다. 이번 조사만으로 운영 환경의 모든 시간 관련 동작을 보장하는 것은 아니다.

재현과 확인

수정 전 동일한 격리 MySQL 8.4.11과 코드에서 JVM 시간대만 바꿔 확인했다.

  • UTC: 세 테스트 모두 CI와 같은 지점에서 실패했고 조회 결과는 null이었다.
  • Asia/Seoul: 같은 세 테스트가 모두 통과했다.

테스트 대상은 ReportMapperIntegrationTest.duplicateLookup*이다. 테스트에는 개발 DB가 아닌 일회용 격리 DB를 사용했다.

수정 방향

테스트 데이터의 상대 생성 시각을 DB에서 CURRENT_TIMESTAMP와 TIMESTAMPADD로 계산해 조회와 같은 DB 시계를 사용한다. 운영 SQL, 10초 기준, 중복 조건 및 기존 단언은 변경하지 않는다.

수정 후 검증

  • UTC: 격리 MySQL에서 전체 빌드와 테스트 1,198건 통과, 건너뜀 0건.
  • Asia/Seoul: 중복 조회 테스트 3건 통과.

두 시간대는 JVM 기본 시간대를 변경해 검증했다. 검증 후 임시 DB 컨테이너를 삭제했다.
