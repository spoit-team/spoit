    02

    환경 설정

    의존성과 DB 설정#

    2.1 Gradle 의존성#

    현재 build.gradle에는 Web MVC·Thymeleaf·Security·WebSocket·MyBatis·MySQL 드라이버와 테스트 의존성이 이미 선언돼 있습니다. 페이지 렌더링만 확인할 때는 의존성을 추가하지 않아도 됩니다.

    Groovy 현재 설치됨 · validation은 선택 
    // 이미 있음 — Thymeleaf 페이지 렌더링
implementation 'org.springframework.boot:spring-boot-starter-thymeleaf'

// 요청 DTO에 @Valid 검증을 붙일 때만 추가
implementation 'org.springframework.boot:spring-boot-starter-validation'
    • Thymeleaf는 현재 의존성과 기본 설정이 적용돼 있어 14개 GET 화면이 렌더링됩니다.
    • Validation 스타터는 아직 없습니다. @NotBlank, @NotNull, @Size, @Min을 실제로 사용할 때 추가합니다.
    • Web MVC·Security·MyBatis·MySQL 드라이버는 이미 선언돼 있으므로 중복 추가하지 않습니다.
    • Spring Boot가 관리하는 라이브러리 버전은 임의로 개별 지정하지 않습니다. 현재 Boot 3.5.16 기준을 유지합니다.
    • 이 문서는 build.gradle을 변경하지 않습니다. 의존성 추가는 실제 기능 구현 작업에서 검토합니다.
    i

    현재 기본 실행은 DB 없이 가능합니다 application.properties가 DataSource·MyBatis 자동설정을 제외하고, 페이지 컨트롤러가 빈 모델을 제공하기 때문입니다. 실제 조회를 붙이는 시점에 아래 설정을 복원합니다.

    2.2 DB·MyBatis 설정 복원#

    현재 application.properties에는 DB URL과 ${DB_USERNAME}·${DB_PASSWORD} 자리표시자가 있지만, 다음 자동설정이 제외돼 있습니다. 실제 DB 개발을 시작할 때 DataSource·트랜잭션·MyBatis 관련 제외를 정리합니다.

    Properties DB 연동 시 적용할 설정 예시 
    # 실제 값은 환경변수로만 주입합니다.
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}

mybatis.configuration.map-underscore-to-camel-case=true
# XML Mapper를 사용할 때만 경로를 추가합니다.
mybatis.mapper-locations=classpath:/mappers/**/*.xml

spring.thymeleaf.cache=false

    DB_URL에는 jdbc:mysql://localhost:3306/spoit처럼 개발 환경의 JDBC URL을 넣습니다. DB 이름·계정·권한·접속 옵션은 개발 환경에 맞춥니다. 비밀번호와 실제 접속 값은 Git·문서에 커밋하지 않습니다. Spring profile 활성화 플래그를 추가하는 방식이 아니라, 기본 설정에서 제외 항목을 정리하는 방식으로 복원합니다.

    • spring.autoconfigure.exclude에서 DataSourceAutoConfiguration, DataSourceTransactionManagerAutoConfiguration, MybatisAutoConfiguration을 제거합니다. UserDetailsServiceAutoConfiguration은 자체 인증을 붙이기 전까지 제외를 유지해 기본 비밀번호 출력을 피할 수 있습니다.
    • 제외를 유지해야 하는 특별한 이유가 있다면 동등한 DataSource·SqlSessionFactory·트랜잭션 빈을 직접 정의해야 합니다. 제외만 해제하고 Mapper를 만들지 않으면 조회가 동작하지 않습니다.
    • mybatis.mapper-locations는 XML Mapper를 사용할 때의 예시 경로입니다. 애너테이션 Mapper만 사용한다면 생략할 수 있습니다.
    • Mapper 인터페이스에 @Mapper를 붙이거나 설정 클래스에 @MapperScan을 적용합니다.
    • 스키마 파일은 src/main/resources/schema.sql이 아니라 루트의 db/schema.sql입니다. 서버 실행만으로 자동 적용된다고 가정하지 않습니다.
    • 종목·지역 등 기준 데이터도 준비해야 합니다. DDL만 적용하면 목록 선택지에 필요한 데이터가 생기는 것은 아닙니다.
    !

    기존 데이터가 있는 DB에 그대로 실행하지 마세요 db/schema.sql에는 DROP TABLE IF EXISTS가 있습니다. 비어 있는 개발용 DB에 검토 후 적용하거나, 운영용 마이그레이션을 별도로 작성합니다.

    i

    문서에는 실제 접속 정보를 남기지 않습니다 예시의 환경변수 이름만 유지하고, 실제 DB 사용자명·비밀번호·운영 URL·세션 키는 문서와 저장소에 기록하지 않습니다.

    연결할 때의 주의사항#

    • HTML 화면은 @RestController가 아니라 @Controller에서 반환합니다.
    • return "matches/list";처럼 반환합니다. templates/ 접두사나 .html 확장자는 붙이지 않습니다.
    • fragments/layout.html, fragments/admin.html은 공통 조각이며 별도 페이지 URL이 필요하지 않습니다.
    • CSS URL은 /css/styles.css입니다. /static/css/styles.css가 아닙니다.
    • HTML을 더블클릭하거나 /templates/matches/list.html로 접속해도 Thymeleaf 렌더링을 확인할 수 없습니다.
    • 같은 서버가 HTML과 폼을 처리하므로 기본 적용에 별도 프런트 서버·REST API·CORS 설정은 필요하지 않습니다.

    루트 진입 컨트롤러#

    현재 루트 진입은 다음처럼 서버에서 /matches로 포워드합니다.

    Java 현재 구현 
    package co.kr.spoit.common;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;

@Controller
public class HomeController {
    @GetMapping("/")
    public String home() {
        return "forward:/matches";
    }
}

    static/index.html은 현재 저장소에서 제거됐습니다. 브라우저 주소는 /로 유지되지만 서버가 /matches 뷰를 렌더링합니다. 302 리다이렉트가 아니며, 새 정적 진입 파일을 다시 추가하지 않습니다.

    04

    화면 모델

    컨트롤러와 화면 모델#

    i

    현재 모델은 자리표시자입니다 CorePageController는 템플릿이 요구하는 속성 이름을 유지하기 위해 빈 목록·null·0을 넣습니다. 이는 기능 구현이 아니라 렌더링 골격입니다. 한 화면씩 GET 컨트롤러 → 페이지/조회 서비스 → MyBatis Mapper → typed 페이지 DTO 흐름으로 교체하되, 템플릿이 읽는 모델 이름과 중첩 구조는 유지합니다.

    4.3 컨트롤러 연결 형태#

    다음은 서비스를 구현한 뒤 사용할 구조 예시입니다. MatchPageService는 현재 저장소에 없으며 직접 작성해야 합니다. listModel(...)은 위 표의 화면 모델 전체를 반환하는 메서드로 가정합니다. 반환값에는 검증되지 않은 요청값이나 비밀번호를 넣지 않습니다.

    Java 서버 예시 · 미구현 
    package co.kr.spoit.match;

import java.util.List;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;

@Controller
public class MatchController {
    private final MatchPageService matchPageService;

    public MatchController(MatchPageService matchPageService) {
        this.matchPageService = matchPageService;
    }

    @GetMapping("/matches")
    public String list(
            @RequestParam(name = "sportId", defaultValue = "all") String sportId,
            @RequestParam(name = "regionId", defaultValue = "all") String regionId,
            @RequestParam(name = "date", required = false) String date,
            @RequestParam(name = "hours", required = false) List<String> hours,
            Model model) {
        model.addAllAttributes(matchPageService.listModel(
                sportId, regionId, date, hours == null ? List.of() : hours));
        return "matches/list";
    }

    // 기존 링크 호환용 경로. 같은 모델 계약, 별도 뷰.
    @GetMapping("/matches/cards")
    public String cards(
            @RequestParam(name = "sportId", defaultValue = "all") String sportId,
            @RequestParam(name = "regionId", defaultValue = "all") String regionId,
            @RequestParam(name = "date", required = false) String date,
            @RequestParam(name = "hours", required = false) List<String> hours,
            Model model) {
        model.addAllAttributes(matchPageService.listModel(
                sportId, regionId, date, hours == null ? List.of() : hours));
        return "matches/cards";
    }
}

    이 예시는 목록 표시의 골격입니다. MatchPageService가 Mapper에서 조회한 행을 템플릿 계약에 맞는 typed 페이지 DTO로 조립하고, 컨트롤러는 뷰 이름만 선택합니다. 공통 로그인 정보는 @ControllerAdvice의 @ModelAttribute 등으로 인증 정보에서 제공하고, 화면 서비스가 잘못 덮어쓰지 않도록 합니다.

    /matches/cards는 기존 링크를 받기 위한 호환 GET 경로입니다. 현재 UI에는 두 화면을 전환하는 스위치가 없고, /matches가 카드 그리드 메인입니다. 요청 경로에 따라 뷰를 고르는 분기를 만들지 말고 위처럼 별도 매핑을 유지합니다.

    구현 시 주의사항#

    • 검색에는 all·빈 문자열이 들어오므로 검색 입구에서는 문자열로 받고 검증 후 수치로 변환합니다.
    • sportId·regionId 타입은 선택지 DTO와 search에서 맞춥니다. 문자열 "1"과 수치 1L 비교에 의존하지 않습니다.
    • hours는 반복 파라미터입니다. 단일 문자열로 받거나 첫 항목만 검색하지 않습니다.
    • 시간·정렬·ID를 검증하고 SQL은 MyBatis #{...}로 바인딩합니다. 요청값을 ${...}에 직접 넣지 않습니다.
    • 관리자는 한 템플릿에 여러 패널이 있습니다. hidden은 서버 평가를 멈추지 않으므로 비표시 패널이 참조하는 모델도 준비합니다.

    POST 폼과 참가 신청 흐름#

    6.1 요청 수신 방식#

    기존 폼은 일반 HTML 폼입니다. JSON 전송이 아니므로 보통 @ModelAttribute 또는 @RequestParam으로 받습니다. @RequestBody를 전제로 구현하지 않습니다.

    팀 참가 선택에는 다음 형태의 DTO를 준비합니다.

    Java 서버 예시 · 미구현 
    // DTO 구조 예시. 각 필드의 getter/setter를 구현해야 합니다.
public class MatchSelectionForm {
    private String applicationType;       // individual | team
    private Long clubId;                  // 개인 참가에서는 전송되지 않음
    private List<Long> clubMemberIds = new ArrayList<>();
}

    위 코드에는 java.util.List·java.util.ArrayList import가 필요합니다. private 필드만 선언하면 일반 프로퍼티 바인딩이 되지 않습니다. getter/setter 또는 적절한 생성자 바인딩을 구현합니다.

    • applicationType은 허용값을 검증합니다. team이면 clubId와 대상 팀원을 검증합니다.
    • 개인 참가에서는 팀 관련 입력이 disabled여서 전송되지 않습니다. 필드 누락을 정상적으로 처리합니다.
    • 체크하지 않은 체크박스도 파라미터가 아예 없을 수 있습니다. 복수 입력은 빈 목록, 동의값은 미동의로 처리합니다.
    • clubMemberIds는 회원 ID가 아니라 club_member.club_member_id 목록입니다.
    • 신청자의 userId·연락처·권한·요금·잔여 좌석은 전송값을 믿지 않고 인증 정보와 DB에서 읽습니다.

    GET /matches/{matchId}

    !

    신청 완료는 결제 완료가 아닙니다 현재 폼은 참가비·취소 안내 확인이며 실제 결제 서비스는 별도 설계가 필요합니다. 표시용 결제 수단 라디오값을 결제 요청으로 처리하지 않습니다.

    POST 후에는 원칙적으로 PRG(POST → Redirect → GET)를 적용합니다. 성공 문구는 저장 성공 후에만 표시하고, 업무 오류는 입력값과 화면 계약에 맞는 error 등을 반환합니다. @Valid를 쓰면 BindingResult를 대상 폼 인자 바로 뒤에 두고, 오류 시에도 선택지·공통 모델을 다시 설정합니다.

    로그인·권한·CSRF#

    7.1 현재 보안 상태와 전환#

    현재 SecurityConfig는 모든 요청을 permitAll로 허용하고 form 로그인·HTTP Basic을 비활성화합니다. CSRF는 기본값대로 켜져 있습니다. 이는 페이지 렌더링을 위한 임시 설정이며, 관리자 URL을 포함한 모든 화면이 비로그인으로 열립니다. 실제 인증 구현으로 오인하지 않습니다.

    실제 개발로 전환할 때는 다음 순서를 지킵니다.

    • CSRF는 유지합니다. 403 회피를 위해 전역 비활성화하지 않습니다.
    • permitAll을 공개 URL·로그인 필요 URL·관리자 권한 URL 규칙으로 교체합니다. GET과 POST, 구체 경로와 와일드카드 순서를 구분합니다.
    • DB 회원 조회용 UserDetailsService와 PasswordEncoder를 구현하고 로그인 폼의 email 파라미터에 맞춥니다.
    • application.properties의 UserDetailsServiceAutoConfiguration 제외는 자체 인증 빈이 준비된 뒤 정리합니다. 그 전에는 기본 비밀번호가 출력되지 않도록 제외를 유지할 수 있습니다.
    • 인증 성공·실패, 403, 관리자 접근 거부를 MockMvc 보안 테스트로 확인합니다.

    공개·인증·권한 규칙의 목표 기준은 다음과 같습니다. 현재 구현 상태가 아니라 전환 후 목표입니다.

    7.2 기존 로그인 폼과의 대응#

    기존 로그인 폼 필드와 Spring Security 설정·서버 처리의 대응
    폼Security 설정·서버 처리
    POST /loginloginProcessingUrl("/login"). 보통 Security 필터가 처리
    emailusernameParameter("email"). 기본값인 username이 아님
    passwordpasswordParameter("password")

    Security DSL의 해당 부분은 다음 형태입니다. 완성된 SecurityConfig가 아닙니다. 공개 범위·사용자 조회·실패/성공 핸들러 등을 별도로 구성합니다.

    Java Security 예시 · 미완성 
    http.formLogin(form -> form
        .loginPage("/login")
        .loginProcessingUrl("/login")
        .usernameParameter("email")
        .passwordParameter("password")
        .failureUrl("/login?error")
        .permitAll());
    • GET /login 컨트롤러에서 auth/login을 반환합니다. ?error가 있으면 사용자용 문구를 error 모델에 설정합니다. 원본 예외나 SQL 오류를 노출하지 않습니다.
    • UserDetailsService는 이메일로 app_user를 조회하고 저장된 password_hash와 역할을 Security에 전달합니다. 비밀번호는 적절한 PasswordEncoder로 검증합니다.
    • 인증 성공 후 검증된 redirect, 저장된 요청, 기본 페이지 등 이동 우선순위를 정합니다. 외부 URL·// 시작·역슬래시·제어문자 등을 거부하고 허용한 앱 내부 경로로만 이동합니다. hidden 값을 무조건 sendRedirect하지 않습니다.
    • 매치 상세의 로그인 링크는 해당 상세 화면으로 돌아갈 경로를 전달합니다. 성공 핸들러를 구현하지 않으면 이 명시적 복귀값이 자동 적용되지 않습니다.
    • 로그인 상태 유지는 체크박스만으로 작동하지 않습니다. remember-me 서비스·비밀키 관리·Cookie 속성·만료 및 로그아웃 처리를 구현합니다.
    • 폼의 member/facility/system과 Security의 GrantedAuthority는 별개입니다. 예를 들어 hasRole("SYSTEM")이면 인증 측에서 ROLE_SYSTEM을 부여합니다. 신청값 role=system만으로 관리 권한을 주지 않습니다.

    • 검증: 마지막 한 자리에 동시 요청, 개인/팀 중복 회원, 소속이 끝난 clubMemberId, 재전송, 취소 후 재신청, receiptNo와 applicationId 혼동.

    3. 가입 승인은 팀 행 등 일관된 잠금 기준으로 정원·신청 상태를 재조회하고, club_member 삽입·신청 상태/processed_at 갱신을 함께 처리합니다. 승인 버튼을 두 번 눌러도 소속 행이 두 개 생기면 안 됩니다.
    4. 팀장 위임은 현재 팀장의 권한과 대상 활성 소속을 확인한 후 기존·새 팀장 역할을 함께 변경합니다. DB는 팀당 활성 팀장 1명이나 최소 1명을 강제하지 않습니다.
    5. 탈퇴·추방은 소속 행을 삭제하지 않고 left_at·leave_type·필요한 사유를 기록합니다. 추방 사유는 현재 폼에 없어 수집·정책이 필요합니다. kick_reason의 NOT NULL이 SQL로 항상 강제된다고 단정하지 않습니다.

    • 반려 reason의 전용 저장 컬럼은 match_application에 없습니다. UI에서 사유를 받으므로 기록 위치·보존·노출 정책을 정해야 합니다.

    처리 순서와 경합 구현 권고

    1. 확정·반려 전에 신청과 경기의 최신 상태, 시설 담당 권한, 이미 처리된 신청인지 확인합니다.

    3. 여러 참가자의 팀 이동은 하나의 트랜잭션과 일관된 잠금 순서로 처리해 동시 이동의 정원 초과를 막습니다.
    4. 이용 완료 시 양 팀 배정과 확정 참가자 전체 배정, 팀 정원을 검증하고 bothTeamsAssigned를 일관되게 구성합니다. 완료 후 팀 구성을 잠그는 현재 화면 정책도 서버에서 강제합니다.
    5. 확정·반려·완료에서 감사 로그와 알림을 실제로 기록할지, 생성 시점과 업무 저장 실패 시 함께 롤백할지 분리할지 결정합니다.

    • 자동 배정 알고리즘, 결과 제출·검토 UI, result_status 값 집합은 현재 SQL·화면에 없습니다.

    • audit_log(528~539): audit_log_id, nullable actor_user_id, action, target_type, 문자열 target_id, detail, created_at. 대상 레코드 FK가 아니며 append-only나 변경 불가도 DB가 강제하지 않습니다.
    • 감사 detail에 비밀번호·초대 코드·세션 토큰 등을 남기지 않습니다. 감사 로그 보존·변경 권한·삭제 정책을 정합니다. 화면의 log.requestId 같은 추적 표시는 SQL audit_log_id와 다릅니다.

    2. 개인 알림과 관리자 알림 모두 수신자 본인 또는 허용된 관리자 역할을 매 요청에서 확인합니다.
    3. 읽음·삭제는 대상 ID만으로 처리하지 않고 recipient_user_id 조건을 함께 사용합니다.
    4. 감사 로그는 현재 자동 기록되지 않습니다. 실제 기록 서비스를 구현하고, 주요 변경과의 트랜잭션 경계·개인정보·비밀값 비노출·삭제·보존 정책을 정합니다.

    CREATE DATABASE spoit DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
    bash
    DB_USERNAME=... DB_PASSWORD=... ./gradlew bootRun

    4. 공통 모델과 조각

    • currentMember: 로그인 회원(userId, nickname, 필수 phone, 표시용 initial 등). null이면 비로그인입니다.
    • unreadCount: 읽지 않은 일반 알림 수. 비로그인은 0을 제공합니다.
    • _csrf: Spring Security 사용 시 CSRF 객체입니다. 템플릿은 _csrf != null일 때만 hidden input을 렌더링합니다.
    • active: siteHeader(active)의 현재 메뉴 강조 값입니다. matches, teams, mypage, admin 중 하나를 전달합니다.
    • styles: head(title, description, styles) 조각에 전달하는 페이지 전용 CSS 파일명 목록입니다.

    6. 폼·CSRF·권한 규칙

    • 상태를 바꾸는 모든 요청은 POST입니다. 검색·필터만 GET입니다.
    • 폼은 method와 th:action="@{...}"를 명시합니다.
    • Spring Security를 사용하는 경우 모든 POST 폼에 다음 hidden input을 둡니다.
    html
    <input type="hidden" th:if="${_csrf != null}" th:name="${_csrf.parameterName}" th:value="${_csrf.token}" />
    • 가짜 CSRF 토큰을 만들지 않습니다. _csrf가 없으면 서버 설정 문제로 보고, 템플릿에서 임의 값을 생성하지 않습니다.
    • 서버는 로그인·회원·팀장·시설 관리자·시스템 관리자 권한을 매 요청마다 확인합니다.
    • 화면에서 버튼을 숨기는 것은 보조 수단일 뿐이며, 서버 권한 검사를 대체하지 않습니다.
    • 로그아웃, 알림 읽음·삭제, 신청 취소, 프로필 저장, 탈퇴, 팀 변경, 관리자 조치는 모두 서버 폼 전송입니다.

    • 개인·팀 평균 레이팅은 0.00~5.00 두 자리 숫자로 표시합니다. 서버 값이 없으면 기록 없음입니다.

    • 정원 또는 남은 좌석보다 선택 인원이 많으면 접수하지 않습니다. 초과 인원 팀을 대기 신청으로 등록하지 않습니다.
    • SQL의 FACILITY_SPORT.default_min과 SOCIAL_MATCH.min_participants는 필수지만 현재 제품은 최대 인원만 사용합니다. 프런트에 최소 인원 필드를 추가하지 않으며, 대상 백엔드/스키마에서 이 충돌을 해소해야 합니다.
    • db/schema.sql은 AUTO_INCREMENT, DEFAULT, CHECK, 외래 키를 선언합니다. 서버도 권한·상태 전이·중복 신청과 같은 업무 규칙을 검증해야 합니다.
    • 신청 접수·확정 대기·참가 확정·이용 완료는 서버 상태로 구분합니다. 이 SQL/화면 계약에는 결제 상태가 없으므로 결제 안내를 결제 완료/미완료 상태처럼 표시하지 않습니다.
    • 날짜·시간·금액은 서버가 포맷한 문자열을 우선 사용합니다. 템플릿은 빈 목록과 null을 안전하게 처리합니다.
    • 빈 상태, 오류 상태, 비로그인 안내, 권한 없음 안내를 유지합니다.

    • 약관·개인정보 문서의 최종 문구와 버전 관리

    현재 db/schema.sql은 MySQL 8용 DDL입니다. app_user에 대표 종목 필드가 없고, user_region/club_region은 여러 지역을 허용하지만 현재 화면은 한 지역만 받습니다. 시설의 사람 수 capacity, 시설 region/좌표 취득, facility_sport 필수 기본값, 매치 안내 note, 팀 실력 level, 시설 요청·점검·CMS·운영 설정·오류 모델, 신고 우선순위, 감사 결과·요청 ID는 SQL과 화면 사이에 직접 대응되는 저장 계약이 없습니다. 또한 facility_sport.default_min·social_match.min_participants는 SQL에서 필수지만 현재 제품은 최대 인원만 사용하며, A/B 자동 확정 정책은 SQL의 MANUAL 기본·AUTO 추천 설명과 다릅니다. 서버/스키마가 이 차이를 해소해야 하며 프런트는 이를 임의로 추정하지 않습니다.

    10. 디자인·접근성

    • 기존 SPO:IT 색상 토큰, 타이포그래피, 얇은 경계선, 플랫한 표면을 유지합니다.
    • /matches는 16:9 시설 사진이 상단에 오는 카드 그리드 메인입니다. 640px 미만 1열, 640px 이상 2열, 1080px 이상 3열입니다.
    • /matches/cards는 호환 경로이며 같은 카드 계약을 사용합니다. playon-match-cards.css는 두 경로에서 사용하므로 삭제하지 않습니다.
    • 키보드 포커스, aria-current, aria-expanded, aria-selected, 모달 포커스 트랩, ESC 닫기, 배경 클릭 닫기를 유지합니다.
    • 모바일 메뉴, 관리자 사이드바, 탭, <dialog>의 포커스 복귀 동작을 유지합니다.
    • prefers-reduced-motion과 공통 포커스 스타일을 약화하지 않습니다.
    • 이미지에는 의미 있는 alt를 제공하고, 장식 이미지는 alt=""와 aria-hidden="true"를 사용합니다.

    11. 실제 개발 연결 방법

    1. 템플릿·정적 리소스는 이미 src/main/resources에 있습니다. 다른 프로젝트로 복사하는 이관 작업이 아니라 src/main에서 데이터 연결을 진행합니다.
    2. application.properties의 DataSource·MyBatis 자동설정 제외를 정리하고 DB 환경변수를 설정합니다. Spring profile 플래그는 추가하지 않습니다.
    3. 화면별 GET 컨트롤러를 CorePageController의 해당 매핑과 교체하고, 페이지/조회 서비스 → Mapper → typed 페이지 DTO로 템플릿 모델 계약을 채웁니다.
    4. GET /는 forward:/matches를 유지합니다. static/index.html은 제거됐으므로 다시 추가하지 않습니다.
    5. 같은 URL에 중복 @GetMapping을 만들지 않습니다. preview 컨트롤러·fixture를 제품 소스로 복사하지 않습니다.
    6. 모든 링크·리소스는 @{...}를 사용하므로 context path가 달라도 동작합니다.
    7. 현재 템플릿은 Tailwind Browser CDN과 Pretendard CDN을 사용합니다. 운영 환경에서는 Tailwind CLI 빌드와 자체 호스팅 적용 여부를 결정합니다.
    8. 시설 사진은 저장소에 포함된 이미지를 사용하되, 운영 전 사용 권한을 확인합니다.

    팀 협업 규칙#

    1. 브랜치 구조

    브랜치 용도 병합 권한
    main 배포용. 병합되면 자동 배포 팀장만
    develop 개발 통합 브랜치 (기본 브랜치) 팀원 승인 1명 이상 후 누구나
    feature/*, fix/* 등 개인 작업 브랜치 -

    main, develop에는 직접 push할 수 없습니다. 모든 변경은 PR로 올립니다.

    2. 작업 흐름

    bash
    # 1) 항상 최신 develop에서 시작
git checkout develop
git pull origin develop

# 2) 작업 브랜치 생성
git checkout -b feature/RES-03-match-apply

# 3) 작업 후 커밋
git add .
git commit -m "feat(match): 개인 참가 신청 API 추가"

# 4) push 후 GitHub에서 develop으로 PR 생성
git push origin feature/RES-03-match-apply
    • PR은 다른 팀원 1명 이상의 승인을 받아야 병합할 수 있습니다.
    • feature → develop 병합은 Squash and merge를 사용합니다.
    • develop → main 병합은 팀장이 Create a merge commit으로 진행합니다.
    • 병합된 브랜치는 다시 사용하지 않습니다. 새 작업은 최신 develop에서 새 브랜치로 시작합니다.
    • 병합된 브랜치는 PR 화면의 Delete branch로 정리합니다.

    3. 브랜치 이름

    text
    {타입}/{요구사항ID}-{짧은-설명}
    타입 용도 예시
    feature 새 기능 feature/RES-03-match-apply
    fix 버그 수정 fix/RES-05-cancel-capacity
    refactor 기능 변화 없는 코드 개선 refactor/MAT-02-rating-service
    docs 문서 docs/readme-setup
    chore 설정, 빌드, 의존성 chore/gradle-mybatis
    • 요구사항 ID는 요구사항 정의서의 ID(COM-01, RES-03, MAT-02, FAC-01, ADM-01 등)를 씁니다. 해당 ID가 없는 작업이면 생략합니다.
    • 설명은 영어 소문자와 하이픈(-)만 씁니다.

    4. 커밋 메시지

    text
    {타입}({범위}): {요약}
    타입 의미
    feat 새 기능
    fix 버그 수정
    refactor 리팩터링
    style 코드 포맷, 세미콜론 등 (로직 변화 없음)
    docs 문서
    test 테스트 추가·수정
    chore 빌드, 설정, 의존성
    • 범위(scope)는 도메인 이름을 씁니다: user, facility, match, club, rating, admin, common
    • 요약은 한글로, 50자 이내, 마침표 없이 씁니다.
    text
    feat(match): 동호회 단위 참가 신청 기능 추가
fix(club): 탈퇴 후 재가입 시 중복 소속 오류 수정
chore(common): MyBatis 매퍼 경로 설정

    5. 로컬 설정

    1. 기본 페이지 렌더링은 .\gradlew.bat bootRun으로 DB 없이 실행합니다. 이때 application.properties의 자동설정 제외를 그대로 둡니다.
    2. 실제 DB 조회를 붙일 때는 DataSource·트랜잭션·MyBatis 제외를 정리하고 DB_USERNAME·DB_PASSWORD 환경변수를 설정합니다. Spring profile 활성화 플래그를 쓰지 않습니다.
    3. application-local.properties.example은 참고용입니다. 실제 비밀번호·API 키·운영 URL은 문서와 Git에 커밋하지 않습니다.

    6. DB 스키마 변경

    • 테이블·컬럼 변경은 ERD와 스키마 SQL 파일을 함께 수정해 PR에 포함합니다.
    • PR 설명에 변경한 테이블과 이유를 적고, 팀원에게 공유합니다.
